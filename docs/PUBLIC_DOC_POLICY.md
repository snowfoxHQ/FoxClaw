# 公开文档书写规范

本规范适用于所有随仓库、公开包、GitHub Pages 或对外渠道发布的 Markdown 文档（README、CHANGELOG、`docs/` 下会进入公开树的文件）。目标是让用户看懂**怎么用**，同时不把内部实现变成公开信息。

判断一句话该不该写，只问一个问题：**删掉它，用户会不会不知道怎么使用、怎么配置、或者产品做了什么？** 不会，就删掉。

## 一、信息分级

| 级别 | 内容 | 公开策略 |
|---|---|---|
| L1 用户功能 | 能做什么、不能做什么、兼容性、使用变化、用户可见行为 | 完全公开 |
| L2 技术能力 | 架构理念、可靠性改进、安全原则 | 适度公开：只讲理念和效果，不讲实现 |
| L3 内部实现 | 精确调用链、内部配置开关、策略细节、防护薄弱点、实现参数、内部路径与符号名 | 不进公开文档 |

L3 内容放私有 Wiki 或不公开目录，不随仓库分发。开源不等于公开全部内部实现。

## 二、对外文档只讲「怎么用」，不讲「怎么实现」（最高优先级）

可以写：

- 用户能做什么、产品新增了什么能力；
- 用户需要怎么配置（工作目录、访问密钥这类**用户必须知道的安全配置**可写，但只写「怎么设」和「设了有什么效果」，配置项名称按实际文档列出）；
- 可靠性与安全方面的**承诺和结果**（例如「治理服务不可用时，高风险操作不会绕过安全限制」）。

不要写：

- 架构图、内部接口、内部模块路径、类名、函数名、字段名；
- 调用顺序、执行链结构、状态机、内部数据格式；
- 部署拓扑、内部服务地址、进程划分、内部工作流；
- 精确的安全开关组合、阈值、超时、有效期等实现参数。

一个方便的界限：**配置项本身可以列，配置在代码里如何生效不列。**

## 三、更新日志脱敏

更新日志说明「这个版本用户得到了什么」，不是开发过程记录。

- 安全修复统一写「修复若干安全问题」「增强操作授权」「加强隐私保护」，**不点名具体漏洞、攻击面、受影响版本或利用条件**。
- 内部接口变更、内部重构、测试与发布治理细节不写进公开 CHANGELOG。
- 不写具体的安全开关、绕过边界、防护机制的不足或限制。
- 用户可见的行为变化照常写（功能上线/下线、边界变化、需要用户做的事）。

对照示例：

| 不写 | 改写为 |
|---|---|
| 「堵住若干具体可利用面（含具体漏洞名称与数量）」 | 「修复若干安全问题，增强操作授权」 |
| 「某拦截机制挡不住刻意变形的输入，所以默认拒绝」 | 「高危操作默认禁止，需显式启用」 |
| 「某开关设为特定值可关闭默认拒绝」 | 「可在配置中调整，详见配置指南」 |
| 「某接口改用一次性凭证，绑定参数指纹、限时过期」 | 「写操作需用户逐次确认，确认不可复用」 |
| 「某函数调用某内部服务失败时降级」 | 「治理服务不可用时不会绕过安全限制」 |

## 四、仓库层面管控

- **分级存放**：需要写实现细节的文档放私有仓库、私有 Wiki 或不公开目录（当前仓库为 `docs/internal/`，已被 `.gitignore` 与公开树同步脚本排除）。
- **公开树白名单**：新增根目录 Markdown 前确认它在允许清单内；公开树由 `tools/sync_public.ps1` 构造，新增排除路径时同步更新该脚本与 `.gitignore`。
- **分支保护**：`main` 作为唯一对外分支，禁止直接提交内部设计文档；发布只从受保护分支进行。
- **本地文件隔离**：本地配置、密钥、调试输出、临时产物进 `.gitignore`，任何密钥只通过环境变量或 `.env` 注入。
- **包内容检查**：npm / wheel 打包前确认产物不含内部文档与调试残留。

## 五、脱敏规则速查

| 敏感类型 | 处理方式 |
|---|---|
| 精确配置开关与安全效果的绑定关系 | 换成用户可见效果描述，细节留在配置指南 |
| 敏感路径、凭据目录、危险命令清单 | 只说「敏感位置始终受保护」「工作目录限制」 |
| 确认协议实现（nonce、指纹、有效期、消费次数） | 只说「需用户逐次确认，不可复用」 |
| 内部 API 路由、函数、类、字段、模块路径 | 删除；必要时说「通过界面/SDK 使用」 |
| 防护薄弱点、绕过手法、明确不覆盖的攻击面 | 删除；改为正向的能力边界说明 |
| 具体参数、阈值、超时、并发数、成本细节 | 删除或改为量级参考 |
| 具体漏洞名称与受影响版本 | 统一为「修复若干安全问题」 |
| 内部测试、发布流程、仓库治理细节 | 移入私有文档 |

## 六、发布前检查清单

提交或同步公开文档前逐项确认：

- [ ] 只讲用户功能、配置方法与可见行为，没有实现细节
- [ ] 没有内部模块路径、类名、函数名、字段名、API 路由清单
- [ ] 没有精确安全开关组合、阈值、有效期、协议参数
- [ ] 没有敏感路径清单、危险命令清单、绕过手法
- [ ] 没有漏洞点名、受影响版本、攻击面说明
- [ ] 安全修复统一用概括表述
- [ ] 用户必须知道的安全配置保留在配置文档中，且只写「怎么设」
- [ ] 中英文版本内容同构、版本顺序一致
- [ ] 新增文件不在公开树排除清单内时，确认它确实适合公开
- [ ] 密钥、`.env`、调试输出未被提交

## 七、例外

用户必须知道如何安全配置产品时（例如工作目录限制、访问密钥、浏览器操作授权），允许在**面向用户的配置文档**中列出配置项及设置方法，但不同时披露内部防护机制与绕过边界。这类内容不写进 CHANGELOG。
